# Project: Revie (heyrevie.com) — Sharetribe + Nylas calendar integration

This repo is a fork of `sharetribe/web-template`, the client app for a coach<>client coaching marketplace (heyrevie.com), built on Sharetribe's Marketplace API.

## Goal
Replace/extend Sharetribe's built-in booking calendar with a real calendar/scheduling integration (Nylas), so clients book coaching sessions against a coach's actual connected calendar while Sharetribe continues to handle listings, coach<>client matching, and payment (Stripe Connect, via Sharetribe).

## Working in this repo

### Commands
- Package manager is **yarn** (not npm). Node `^22.22.0 || >=24.0.0`.
- **Run the app:** `op run --env-file=.env -- yarn dev` — starts the React frontend (`scripts/start.js`) and the Express backend (`nodemon server/apiServer.js`) together; backend API on port 3500. The `op run` wrapper injects secrets from 1Password (see the secrets decision below); plain `yarn dev` still runs but without real secrets.
- **If `op` fails from Claude's shell, grant VS Code the macOS Automation permission.** 1Password's desktop app integration authorises *per calling application*, and needs macOS permission for that app to drive it. The symptom is `op` reporting `You are not currently signed in` or `No accounts configured` to Claude while `op vault list` works fine in your own integrated terminal. The fix is **System Settings → Privacy & Security → Automation → allow Visual Studio Code to control other programs**, then restart VS Code; after that `op run` works from Claude's shell, including backgrounded commands. Re-ticking "Integrate with 1Password CLI" alone does not fix it, and `op account add` works but writes derived key material into `~/.config/op/config`, whereas the app integration stores nothing on disk. If the permission cannot be granted, the fallback is to run `op run --env-file=.env -- yarn dev` yourself and let Claude verify over HTTP, which needs no secrets.
- **`op run` can start the app with references *unresolved* rather than failing.** If the 1Password authorisation prompt is not answered in time, `op run` does not necessarily abort — the app starts normally with variables holding the literal `op://Revie Dev/…` string. Nothing complains until something uses one, and then the error comes from a third party and points nowhere useful: Google answered a login attempt with `Error 401: invalid_client`, because the client id it received was the string `op://Revie Dev/google_login_oauth/client_id`.
  - **After starting the dev server, check a value actually resolved** rather than assuming: `curl -sD- http://localhost:3500/api/auth/google -o /dev/null | grep -i location` shows the Google authorize URL, and a `client_id=op%3A%2F%2F…` in it means the whole process is running on placeholders. The same check works for any endpoint that puts a credential into a URL.
  - The fix is simply to restart the server once `op` is working, but the symptom is worth recognising because it looks like a misconfigured OAuth client rather than a secrets problem.
- **Claude's shell authenticates with a read-only 1Password service account, not the desktop app.** A guarded export gives Claude a token while leaving interactive terminals on the personal account, so `op item create` and the other vaults still work when a human runs them:
  ```sh
  # in ~/.zshenv - NOT ~/.zshrc
  if [ -n "$CLAUDECODE" ]; then
    export OP_SERVICE_ACCOUNT_TOKEN="ops_..."
  fi
  ```
  - **It must be `~/.zshenv`.** Claude's shell is non-interactive and zsh reads `.zshrc` only for interactive shells, so a token placed there silently never arrives — which looks exactly like the token being wrong. `CLAUDECODE` is set in Claude's shell and not in a human's, which is what keeps the two apart while both read the same file.
  - **Scope: `Revie Dev`, read-only.** Verified from Claude's shell: it lists exactly one vault, resolves `Revie Dev` references, resolves all six secrets for running the app, and is refused the `Revie` vault with `"Revie" isn't a vault in this account`. That error is correct behaviour, not a fault — the live Sharetribe and Stripe credentials are genuinely out of reach. Run such commands in a human terminal instead.
  - **This is narrower than what it replaced**, not merely quieter. The desktop app integration gave Claude's shell whatever the signed-in human could see — every vault — for as long as the app stayed unlocked. Widening the auto-lock window to stop the interruptions would have widened that further; the service account removes the prompts *and* cuts access to one vault, read-only, with its use logged.
  - The token record lives outside `Revie Dev` on purpose, so the credential is not stored inside the thing it unlocks.
- **Diagnosing `op` when it stops working:** `op whoami` is ambiguous — it says the same thing whether the app is locked, the CLI integration is off, or no account is configured. `op account list` is the one that distinguishes them: empty means the CLI genuinely has no account. Prefer re-enabling **Settings → Developer → Integrate with 1Password CLI** over `op account add`, because the manual path writes derived key material into `~/.config/op/config` whereas the app integration stores nothing.
- **Tests:** `yarn test` (client, Jest) and `yarn test-server` (Express server tests). `yarn test-ci` runs both.
- **Format:** `yarn format` (Prettier over `**/*.{js,css}`); CI enforces it via `yarn format-ci`.
- **Config:** `yarn config-check` validates `src/config/` against the connected Sharetribe environment. `yarn build` produces the production bundle; `yarn start` serves it.

### Repo map
- `src/containers/` — page-level React components. Each container usually has its own `*.duck.js` holding that page's Redux state, action creators, and async thunks.
- `src/ducks/` — global Redux modules (auth, current user, etc.). `src/reducers.js` and `src/store.js` wire everything together.
- `src/components/` — shared presentational components. `src/util/` — helpers (dates, currency, API, validation). `src/transactions/` — client-side transaction-process helpers.
- `src/config/` — **marketplace** configuration (branding, listing types, search, Stripe), validated by `yarn config-check`. Most of it is normally served from Sharetribe Console as hosted assets, with these files as the local fallback; `src/util/configHelpers.js` merges the two. Note the root `config/` directory is unrelated — it is webpack/build config only.
- `server/` — the Express server: server-side rendering (`server/renderer.js`) plus API endpoints (`server/apiRouter.js` → `server/api/`).
- `server/api/` — server-only endpoints. **Privileged transitions already live here:** `initiate-privileged.js`, `transition-privileged.js`, `transaction-line-items.js`. New privileged/webhook endpoints for the Nylas backend belong here (or a sibling folder), registered in `server/apiRouter.js`.
- `ext/transaction-processes/` — reference copies of the Sharetribe transaction processes (`default-booking`, etc.), each with a `process.edn` definition and a `templates/` folder of notification emails. These are edited here and pushed to Sharetribe with the Sharetribe CLI; the *active* processes actually live in Sharetribe Console.
- `patches/` — `patch-package` patches (currently `final-form` and `@testing-library/user-event`), reapplied on every `yarn install` via the `postinstall` script. If a dependency behaves unexpectedly, check here first.

### Where "our own backend" lives (decided)
The Nylas webhook handler and the privileged-transition caller live **inside this repo's `server/` directory**, under `server/api/nylas/`. One deploy to Render, and it reuses the Sharetribe SDK and secret handling already in `server/api-util/sdk.js`. Keep all Nylas code inside that subfolder so it can be extracted into a standalone service later without untangling it from template code.

Two things the template does not give us for free here:
- **The Integration SDK is not installed.** `package.json` has `sharetribe-flex-sdk` but not `sharetribe-flex-integration-sdk`. `getTrustedSdk` works by exchanging the *logged-in user's* cookie token, so it cannot serve a user-less webhook. Webhook-driven transitions need the Integration SDK plus `SHARETRIBE_INTEGRATION_CLIENT_ID` / `_SECRET`.
- **`server/apiRouter.js` only parses `application/transit+json`.** A plain-JSON webhook POST arrives unparsed, and there is no CSRF protection or request authentication anywhere in the codebase. A webhook route needs its own `bodyParser.json({ verify })` to keep the raw body for Nylas's HMAC-SHA256 signature check, and every new state-changing endpoint must identify its caller with an SDK call before acting.

### The Sharetribe environments, and how they differ
Sharetribe provides **three** environments, and this matters more than it first appears. **Dev** (`revie_dev`, client id `f04578ab…`) is the only one that supports custom code, so it is the correct target for this project. **Test** (`af76dace…`) is a no-code preview meant to mirror Live. **Live** (`7601334b…`) is production. Configuration is served per-environment as hosted assets from Console, so they drift silently.

**Copying is directional.** Console's "Copy changes to…" button lives in **Test** and pushes to Dev and Live; there is no Live → Test or Live → Dev copy. So the supported way to fix a stale Dev is to make Test correct and copy Test → Dev. Note this also means editing Live directly bypasses the intended flow and is how Live and Test fall out of step — which has already happened once here, see the field note below.

**The client id selects both configuration and data**, so there is no way to run Dev's data against Live's configuration; pointing the app at Live's client id makes it the Live marketplace, with real coaches and real Stripe charges.

All three were dumped read-only and compared. The core transaction shape matches everywhere: listing type `signature-session`, process `default-booking/release-1`, `unitType: fixed`, `availabilityType: oneSeat`, 20% provider commission.

**The same in both:** listing type `signature-session` ("Signature Session"), transaction process `default-booking/release-1`, `unitType: fixed`, `availabilityType: oneSeat`, 20% provider commission, and six of seven listing fields (`identity`, `communication_style`, `structure`, `language`, `coachlocation`, `pre_work`).

**Where they differ, and why it matters:**

- **Live is a *public* marketplace; test is private.** This corrects an assumption recorded earlier from the test environment alone: it is **not** true that a client is always logged in before reaching a booking UI. On live, `marketplace.private` is `false`, so anonymous visitors can browse listings and can reach a coach's page logged out. **The Nylas booking UI must therefore handle the logged-out case** — prompting sign-in before a booking can be started — rather than assuming a session exists. The client-side privileged-transition path through `getTrustedSdk` needs a logged-in user, so it cannot be treated as always available.
- **Price variations — was drifted, now fixed.** Live and Test both have `priceVariations.enabled: true` while Dev had it off. Resolved by copying Test → Dev, and verified: all three now agree. This was the difference that actually mattered, because listings can carry several priced variants, so the booking panel must render `PriceVariantPicker` and pass `priceVariantName` through in `orderData`. Built against the old Dev config, the Nylas booking UI would have silently ignored variants and charged the wrong price.
- **Approval rules are inverted, and this is intentional — do not "fix" it.** Dev and Test are private with listing approval on; Live is public with user approval to join instead. Keeping the unfinished marketplace unbrowsable while Live is open to the world is a sensible arrangement, so these settings are expected to differ per environment rather than being drift to correct. The consequence for code stands regardless: on Live the gate a coach passes is at signup, not at listing publication, and a logged-out visitor can reach a listing page.
- **Listing fields differ by one, and Live was edited directly to do it:** Dev and Test have `length`, Live has `timezone`. Because the change was made straight in Live rather than in Test and copied forward, Test never received it. Deliberately left unreconciled: The live `timezone` field is a **workaround for Sharetribe having no per-coach timezone**, and this project removes the need for it: Nylas computes availability and timezone from the coach's connected calendar. So do not build anything that depends on `timezone`, and plan to retire the field once the Nylas integration is live. The test-only `length` field is worth checking for staleness.

Note that private mode makes `/s*` paths significant on the test environment — see the comments in `src/routing/routeConfiguration.js` and `server/resources/robotsPrivateMarketplace.txt`.

**Decision (settled): develop against Dev, and keep it in step through Test.** Dev is the only environment that supports custom code, so it was always the right target; the problem was only that its configuration had fallen behind. Pointing the app at Live would need the Extend plan at $299/month and would expose real coaches and real Stripe charges to unfinished code, to buy accuracy that one Console copy provided for nothing. When Console configuration changes in future, make the change in **Test** and copy forward, rather than editing Dev or Live directly.

### Keeping the fork mergeable
The repo was renamed from `sharetribe-template` to **`revie-dev`** so it matches the Render service and the `Revie Dev` 1Password vault; GitHub redirects the old URL, so an older clone keeps working until its `origin` is updated. Note the name is now shared by four things — the GitHub repo, the Render service `revie-dev`, its database `revie-dev-db`, and the deployed site `revie-dev.onrender.com` — which is deliberate, but worth reading carefully when an instruction says "revie-dev".

This repo tracks `sharetribe/web-template` as the `upstream` git remote (origin is `regan-revie/revie-dev`) and periodically merges upstream releases — `v12.3.0` was the most recent. To keep those merges painless, prefer **adding new files** over editing core `src/` files, and concentrate custom logic in `server/api/`, `ext/`, and clearly named new modules. When a core file genuinely must change, keep the diff small and leave a comment explaining why.

## The six requirements that shaped the calendar decision
Sharetribe's built-in calendar can't do these:
1. Coaches do not need to leave the heyrevie.com platform.
2. Coaches can connect their Google / Apple / Outlook calendar easily.
3. Availability and timezones are computed from that connected calendar.
4. Revie defines event types (e.g. "Workshop", "1:1 Session") and coaches choose which ones to sell.
5. Revie controls event styling and reminder emails; third-party branding on the calendar itself is acceptable.
6. Revie can see and track when bookings are created.

## Decisions already made (from prior planning — don't relitigate without new information)
- **Keep Sharetribe as the marketplace engine.** Not building a custom marketplace from scratch — Sharetribe already handles payments, auth, listings, messaging, reviews, and admin, which would be very costly and risky to rebuild.
- **Environment strategy:** develop against a Sharetribe **Build**-plan TEST environment first (cheap, full custom-code access to test data). Only move to the **Extend** plan ($299/mo) and live data once ready to launch.
- **Calendar vendor: Nylas** (Cal.com in every form, and a from-scratch calendar build, were considered and rejected — see below).
  - Cal.com Free/Teams accounts require a coach to visit cal.com's own site (sign up, generate API key, connect calendar) — no embeddable connect-flow on those tiers, so requirement #1 can't be fully met. Cal.com Platform/Atoms *would* embed the whole flow, but per Cal.com's own FAQ it's "now deprecated and under maintenance for existing users only — no new customers can sign up."
  - Cronofy is architecturally a great fit (their flagship case study, Docplanner, is the same marketplace shape) but starts at $819/month — not viable at Revie's current stage.
  - **Nylas** fits: free tier (up to 5 connected calendars, full Scheduler, reminders, webhooks, no credit card), then $15/mo for 10 accounts, $49/mo for 25 — cheaper than Cal.com Teams' flat $12/coach once past a handful of coaches.
    - Requirement #1: use Nylas **"Hosted Authentication" plus whitelabeling** — Revie's own logo and a custom `auth.heyrevie.com` hostname, so the coach never sees a nylas.com URL. **This supersedes an earlier decision to use "Custom Authentication"**, which rested on a misreading of the Nylas docs: Custom Authentication (`POST /v3/connect/custom`) requires the caller to *already hold a refresh token* for the coach's account, so Nylas performs no OAuth handoff at all. Taking that route would mean Revie building and owning a full OAuth integration with Google, Microsoft and Apple separately. Both routes require Revie to own its own Google Cloud project and Azure app registration (whitelabeling needs them to register custom callback URIs), so that cost is unavoidable either way — but Hosted plus whitelabel reaches the same "never leaves Revie" experience with far less code.
    - **Data region: US in development, and this must change before go-live.** The Nylas free sandbox is US-only, so the development application runs in the US region (`api.us.nylas.com`; the EU host rejects the sandbox key). That means coach calendar data — event titles, attendees, times — is processed in the United States, which is not an acceptable resting position if Revie has UK or EU coaches. **Before launch, create a non-sandbox Nylas application in the EU region** and point `NYLAS_API_BASE_URL` at `api.eu.nylas.com`. The region is fixed per application: it cannot be changed later and grants cannot be migrated, so the cost of this rises the moment real coaches connect. Treat it as a go-live blocker, not a nice-to-have.
    - **The free Sandbox cannot meet requirement #1, and meeting it costs more than first assumed.** A Sandbox application ships with Nylas's own pre-configured OAuth connectors. On Sandbox you cannot supply Revie's Google or Microsoft credentials, cannot create connectors, and never see the `client_secret`. **You *can*, however, change an existing connector's scopes** — Nylas's support documentation says otherwise, but it was done here and verified against a real grant, so treat that claim as wrong. The consequence that does hold: coaches see *Nylas* on the Google consent screen until the app leaves Sandbox. The blocker is *Sandbox*, not *paid tier* — a distinction worth keeping straight. **Essentials ($15/month) gives a production application**, which should permit a custom connector with Revie's own Google credentials, and therefore a Revie-branded Google consent screen and the narrowed scopes. What Essentials does *not* buy is Nylas's own hosted-auth page branding or the custom `auth.heyrevie.com` hostname: per the pricing page both are **Pro-tier add-ons**, and Scheduler whitelabeling is **Pro Annual only**.
    - **So requirement #1 splits into two halves with very different prices.** The half that matters most — the Google consent screen the coach actually reads and grants access on — is reachable at Essentials, because that screen is rendered by Google using Revie's own OAuth client. The remaining gap was the brief Nylas-hosted redirect, and **testing showed it is invisible**: passing `provider=google` sends the coach straight to Google's consent screen with no Nylas picker page. So the Pro-only branding add-ons are not worth buying, and Revie builds its own "Connect Google / Outlook / Apple" buttons instead of ever showing Nylas's. Confirm "bring your own auth" availability on Essentials directly with Nylas before paying; the pricing page is ambiguous on that row, and that is now the only thing gating the tier decision.
    - **What still works on Sandbox:** grants (up to 10), Scheduler configurations, and webhooks. The whole integration can therefore be built and tested now, with Nylas branding and the default broad scopes as a known, temporary compromise, and the branding and scope work applied when the app is upgraded. Revie's Google Cloud OAuth client is a prerequisite for that upgrade, so setting it up early is not wasted — it is simply parked until there is a production application to attach it to.
    - **Request calendar scopes only, and narrow them deliberately.** Nylas's *default* Google connector asks for `gmail.modify` and `contacts` alongside `calendar`, and its default Microsoft connector asks for `Mail.ReadWrite`, `Mail.Send` and `Contacts.ReadWrite`. None of that is needed for scheduling. Revie's own Google connector should request `openid`, `userinfo.email`, `userinfo.profile`, `calendar.readonly` and `calendar.events`, and nothing more. **This is now applied and verified**, not aspirational. The Google connector on the Sandbox app requests exactly `openid`, `userinfo.email`, `userinfo.profile`, `calendar.readonly` and `calendar.events`, and a real grant created through the connect flow came back holding precisely those and nothing else — no `gmail.modify`, no `contacts`. **One caveat, unresolved:** the Google consent screen still *displayed* the broader scope list even though the grant came back narrow. The likely explanation is that Sandbox uses Nylas's own shared Google OAuth app, so Google renders that app's configured scopes rather than the ones actually requested — which would resolve when Revie supplies its own OAuth client on a production application. That is a hypothesis, not a verified fact: **check what the consent screen actually says immediately after upgrading**, because a screen listing Gmail access will cost coach sign-ups regardless of what is really granted.
    - **TO DO before production: narrow the Microsoft connector.** It still requests `Mail.ReadWrite`, `Mail.Send`, `Contacts.ReadWrite` and `People.Read` alongside `Calendars.ReadWrite`. The same three arguments apply as for Google — consent-screen trust, verification burden, and holding data Revie never uses. Must be done before Outlook is offered to any coach. Three reasons this matters: a consent screen asking permission to read, send and permanently delete a coach's email will cost sign-ups and deserves to; Gmail scopes are *restricted*, which drags in Google's CASA security assessment, a cost that calendar access alone does not carry; and holding email access Revie never uses is a GDPR liability with no corresponding benefit.
    - **Why `calendar.readonly` + `calendar.events` specifically.** Nylas's connector UI does not offer Google's narrower `calendar.freebusy`, `calendar.events.owned` or `calendar.calendarlist.readonly` scopes, so this pair is the narrowest workable set on offer: `calendar.events` covers both reading events for availability and creating, updating and deleting booking events, while `calendar.readonly` is what lets Nylas enumerate a coach's calendars and read their timezone. The pair is deliberately chosen over full `calendar`, which grants deleting and sharing whole calendars rather than just events, and reads on the consent screen as "see, edit, share, and permanently delete all the calendars you can access". One consequence to design around: Nylas's `primary` keyword requires the full `calendar` scope, so store each coach's real calendar ID instead — which is better anyway, since coaches should choose which calendar they sell against.
    - Requirement #4: use Nylas **Scheduler Configurations** (host, duration, availability rules), created/updated per coach via API. Revie's backend defines the "Workshop" / "1:1 Session" templates and pushes a configuration to a coach's account when they opt in.
    - Requirements #2/#3/#6 (calendar connections, timezone/availability, webhooks) are core Nylas features across all tiers.
    - Requirement #5 (branding OK) means no need to chase a "remove branding" tier at all.
  - **Booking↔transaction correlation must be captured from the webhook, not queried back.** Nylas staff have confirmed on their own forum that metadata attached to a booking is *not* retrievable through the booking API, and is not inherited by the event Nylas creates. It comes back only in the webhook payload, under `customFields`. So the webhook handler has to durably persist the mapping (Nylas booking id ↔ Sharetribe transaction id) the moment it arrives — there is no way to re-derive it later.
  - **Verify hands-on early in Phase 2** (couldn't confirm from public docs): the actual feel of the Apple/iCloud connect flow — it uses app-specific passwords rather than OAuth, so it may not fit the same UI as Google/Microsoft; whether free/low-tier webhook payloads carry everything needed for the Sharetribe sync; how flexible reminder-email customization is per tier.
- **Booking confirmation is automatic; coaches do not approve bookings.** A client who has paid should not sit waiting for a coach to act, since the coach's calendar already said they were free. **No transaction-process change is needed for this**: `transition/operator-accept` already exists, runs `accept-booking` and `stripe-capture-payment-intent`, and moves `preauthorized → accepted`. Our backend calls it through the Integration API when the Nylas `booking.created` webhook confirms the slot, so acceptance and payment capture happen together, driven by the calendar rather than by a human.
- **Notice periods: booking notice is per coach, cancellation notice is platform policy.** `scheduler.min_booking_notice` is settable per coach ("no bookings within the next N hours"), defaulting to 24 hours because Nylas's own default of 60 minutes is far too short for a session someone must prepare for. `scheduler.min_cancellation_notice` is a global 24 hours and deliberately not per coach. A coach cannot express either in Google Calendar, because Nylas computes availability from free/busy events and never reads Google's own booking-page settings. `available_days_in_future` is clamped to 90 days, because Stripe will not hold a card authorisation longer and a booking beyond it would have its payment expire before the session.
- **Cancellation policy: free before 48 hours, charged inside it. Clients may always cancel.** `scheduler.min_cancellation_notice` is deliberately **0**, not 2880. Blocking Nylas's cancel button inside the window would leave the coach expecting a client who is not coming, and would not keep the money either. Instead a client can always cancel — so the coach's calendar frees up — and the 48-hour threshold decides only whether they are *refunded*. `isFreeCancellation()` in `server/api/nylas/scheduler.js` makes that call, and it throws rather than guessing on a missing or unparseable time, because silently defaulting a refund policy is a billing dispute nobody notices. The boundary is inclusive: cancelling at exactly 48 hours is free.
- **Enforcing the charge needs no new transition — it is achieved by doing nothing.** This was initially scoped as a zero-refund transition to write and push with the Sharetribe CLI. It is not needed. By the time a session is cancelled the transaction is already in `accepted`, meaning payment was captured at acceptance, and `transition/complete` is **time-triggered** at `booking-end + 2 days`, moving `accepted → delivered` and running `stripe-create-payout` by itself. So the webhook handler's rule is simply:
  - **Cancelled more than 48 hours out** → call `transition/cancel` through the Integration API. It runs `calculate-full-refund` and `cancel-booking`, so the client is refunded and the slot released.
  - **Cancelled inside 48 hours** → **do nothing to Sharetribe.** The transaction completes by itself, the client keeps their charge and the coach is paid, which is exactly the intended policy. Only the Nylas calendar event goes.
  - Two costs to accept knowingly: the Sharetribe record will read `delivered` for a session that did not happen, and both parties will be invited to review it. Neither is harmful, and the honest record of "this was a late cancellation" lives in our own database instead — one more reason that database earns its place.
  - This removes the riskiest item from the plan: no change to a live money-handling transaction process, and no CLI push.
- **"Hold the payment and only capture at 48 hours before the session" is not achievable, and the constraint is Stripe's not ours.** A card authorisation lapses after roughly seven days, and the transaction process already encodes this: `transition/expire` fires at the **minimum** of `preauthorized + 6 days`, `booking-start + 1 day`, and `booking-end`, refunding and declining the booking. So a payment held but uncaptured is force-expired after six days. Since the booking window is 30 days and may be up to 90, most bookings would be cancelled by that timer long before their session. Holding until 48 hours before only works if every booking is made within six days of the session, which would mean shrinking the booking window to under a week and crippling the product.
  - **The workable model is therefore: capture at booking, refund on cancellation.** The client-facing promise is identical — "free cancellation up to 48 hours before" — and it is what hotels and most booking marketplaces do. The money simply moves at booking rather than at the 48-hour mark. Cancel earlier than 48 hours: refund, which `transition/cancel` already does. Cancel inside 48 hours: keep the payment, which needs the new zero-refund transition above.
- **The booking↔transaction mapping goes in a Render Postgres database.** Chosen over carrying the id through Nylas `customFields` alone, which cannot be reconciled retrospectively, and over storing it only on the Sharetribe transaction, whose reverse lookup — booking id to transaction — depends on querying transactions by `protectedData`, which is unconfirmed. A database also serves the discount-codes project already on the backlog. Still worth writing the Nylas booking id onto the Sharetribe transaction as well, so a human debugging one booking can see the link in Console.
- **Backend architecture (unchanged regardless of vendor):** our own backend owns confirmation/reminder emails; receives a webhook per coach on booking confirm/cancel/reschedule; calls a Sharetribe **privileged transition** (server-only, secret-key-gated) to move the corresponding Sharetribe transaction forward, keeping payment capture tied to Sharetribe.
- **Hosting target:** Render (Railway as fallback). Needs a host that runs a persistent Node/Express server — serverless platforms are not compatible with the Sharetribe Web Template. **Render now comes early rather than at go-live**: Nylas will not issue a webhook signing secret until it can reach our endpoint over public HTTPS, and `localhost` cannot serve that. The service is defined as a Blueprint in `render.yaml` (region: Frankfurt) so the configuration lives in git rather than only in a dashboard. Two constraints worth remembering: the **free plan is unusable** here, because free services sleep and cold-start in 30+ seconds while the Nylas webhook challenge times out at 10 seconds; and Render sits behind a reverse proxy, so `SERVER_SHARETRIBE_TRUST_PROXY` and `REACT_APP_SHARETRIBE_USING_SSL` must both be `true` or cookies and redirect URLs misbehave.
- **Secrets on Render are the exception to the 1Password rule below.** `op run` is a local-development mechanism; it does not follow the app into production. Deployed secrets are entered into Render's own encrypted environment store, which means secret values legitimately live in two places — 1Password and Render — and `.env` still never holds a real value. (A 1Password service-account token as Render's only secret, with `op run` wrapping the start command, would restore a single source of truth; it was rejected for now because it puts the `op` CLI and a live 1Password dependency in the production boot path. Worth revisiting for the production environment.)
- **Secrets management: 1Password, not plaintext `.env` files.** Real secrets (Sharetribe API keys, Nylas API key/client credentials, Stripe keys, etc.) live as items in a 1Password vault. The `.env` file in the repo holds only `op://vault/item/field` references, never real values, and must stay out of git (confirm it's in `.gitignore`). Run the app via `op run --env-file=.env -- <start command>` so secrets are injected into the process environment only for that run. Never hardcode a secret or print one to a log/commit.

## Current state — Phase 1 done, Phase 2 underway
**Phase 1 is proven.** The stock template runs locally against the `revie_dev` environment: `yarn dev` serves the frontend on :3000 and the API server on :3500, 1Password resolves both Sharetribe credentials through `op run`, the hosted config assets load from the Marketplace API, and the app renders in the browser. The repo is no longer a bare fork: `server/api/nylas/` holds the webhook receiver and the coach calendar connect flow, `render.yaml` defines the deployed service, and `server/apiRouter.js` and `server/index.js` carry small, commented changes to wire them in. Everything else is still upstream.

**The Render dev service is live** at `https://revie-dev.onrender.com`, deployed from the `render.yaml` Blueprint on `main`. Verified against the running service: it server-side renders (184KB of real HTML, versus the dev server's 8.4KB client-only shell), it loads the Sharetribe hosted config — the page title comes back as the real marketplace branding — no `localhost` URL leaked into the production bundle, CSP is active in report-only mode, and the Express API router is mounted, with `/api/transaction-line-items` returning 400 on a bad body and unknown `/api/*` paths returning 404. That last point matters most: it is the proof that a webhook route added under `server/api/nylas/` will actually be reachable. **The webhook URL to give Nylas will therefore be `https://revie-dev.onrender.com/api/nylas/...`.**

**The dev webhook destination exists and is active.** It was created with `POST /v3/webhooks` rather than through the dashboard: the Notifications UI does not list the Scheduler `booking.*` triggers, but the API accepts them, so the dashboard is simply behind. Destination `zpppCExuEvsq74PBxQCbTm0228` points at `https://revie-dev.onrender.com/api/nylas/webhooks` and subscribes to `booking.created`, `booking.pending`, `booking.rescheduled` and `booking.cancelled`. Its `status` came back `active`, which is Nylas confirming our endpoint answered the `?challenge=` check. The secret lives at `op://Revie Dev/nylas_dev_webhook_secret/credential`.

**The webhook path is proven end to end in production.** Against the live Render service: a correctly signed `booking.created` is accepted, a signature made with the wrong secret is rejected, a request with no signature header is rejected, a body tampered with after signing is rejected, and a signed but unrecognised trigger is acknowledged without being handled. **When adding any further webhook route, note the trap this caught:** with CSP enabled, `server/index.js` installs a global `bodyParser.json` matching `'json'` *before* the `/api` mount, which consumes the body first and makes body-parser skip the API router's own parser as already-parsed — so a `verify` hook registered only on the route never fires and `req.rawBody` is undefined. Signatures then fail for genuine requests while forged ones still fail, so the endpoint looks correct and is not. Both parsers now populate `req.rawBody`. The dev API server has no such parser, so this class of bug cannot be reproduced locally and must be checked against a deploy.

Two operational notes worth keeping. **The webhook secret cannot be read back** — `GET /v3/webhooks/{id}` omits it, confirmed against the live API — so the only recovery is `POST /v3/webhooks/rotate-secret/{id}`, which mints a new one and invalidates the old. Rotation is cheap while nothing depends on the value, so if a secret is ever exposed, rotate immediately rather than trying to recover it. And **each destination has its own secret**, so the eventual production service needs its own destination and its own 1Password item.

**Google SSO works on Dev**, locally and on the Render service. It needs three things and all three are done: a Google OAuth client (separate from the Nylas one — different purpose, and SSO uses only the non-sensitive `email`/`profile`/`openid` scopes, so no Google verification); an identity provider client configured in Console **per environment**; and `REACT_APP_GOOGLE_CLIENT_ID` plus `GOOGLE_CLIENT_SECRET` as environment variables, referenced from `.env` as `op://Revie Dev/google_login_oauth/…` and set directly in Render. Sharetribe requires the secret to come from an environment variable rather than Console.

Two things that cost time and will again. The redirect URIs are **`http://localhost:3500/api/auth/google/callback`** — port 3500, because in development the callback goes to the API server rather than the frontend — and `https://revie-dev.onrender.com/api/auth/google/callback`. And `REACT_APP_GOOGLE_CLIENT_ID` is compiled into the bundle at build time and gates whether the button renders at all, so it needs a full rebuild, not a restart. When checking whether it took, **do not grep the production bundle for the client id**: the gate is `!!process.env.REACT_APP_GOOGLE_CLIENT_ID`, which the minifier constant-folds to `showGoogleLogin:!0`, and the id itself never appears client-side because the flow is server-side. The unminified dev build does contain the string, which makes the two builds disagree misleadingly.

**⚠️ Nylas's availability endpoint does not enforce `min_booking_notice`, so we must.** `GET /v3/scheduling/availability?configuration_id=…` returns `data.time_slots[]` in Unix seconds, and with a 72-hour notice configured it returned **719 slots, the first starting six minutes from now**. Nylas applies the notice period only in its own booking UI, which we do not use. `filterSlotsByNotice()` in `server/api/nylas/availability.js` does it instead, verified against live data: 719 slots in, 647 out, first bookable slot moved from 0.1 hours to 72.1 hours away. **This filtering has to stay on the server** — a client-side filter is one devtools edit away from being bypassed, and the failure mode is invisible, since bookings simply start appearing too soon. The endpoint *does* honour `available_days_in_future`, so only the near end of the window needs filtering.

**The availability endpoint is also public**: it answers unauthenticated requests given only a configuration id, so anyone holding one can enumerate a coach's free time. We proxy it through our own server regardless, both to apply the notice filter and to keep configuration ids off the page.

**The booking UI is built and working in the browser.** `NylasBookingForm` replaces `BookingFixedDurationForm` for listings with `calendarBookingEnabled`, switched inside `OrderPanel` so both listing layouts pick it up without changes. It emits the same `bookingStartTime` / `bookingEndTime` / `priceVariantName` values, so line items, checkout and Stripe are untouched. Verified against the real test listing: 20 selectable days, times in the viewer's timezone, a working timezone selector, and unavailable days blocked in the calendar.

Two decisions worth keeping. **Times are shown in the *viewer's* timezone, not the coach's** — an earlier version grouped by the coach's zone so a slot would not appear under the wrong day, which was backwards: a client is picking a slot in their own week, and making them convert from `America/Los_Angeles` is the confusion to remove. And **there is no sign-in gate in the form**, because `CheckoutPage` is declared `auth: true` and the router already redirects a logged-out visitor and returns them, which matters on the public live marketplace.

**⚠️ Three Nylas Scheduler traps, all found by testing rather than reading.** Each is accepted with a 200 and then silently misbehaves:
- **`min_booking_notice` is not applied by the availability endpoint** (recorded above) — filter it yourself.
- **Working hours are `default_open_hours`, not `open_hours`.** The latter is accepted and discarded with no error.
- **The `timezone` inside `default_open_hours` is stored but ignored**; start and end are computed as **UTC**. Asking for `09:00–17:00 America/Los_Angeles` gave the coach 02:00–09:00 their time, and reading the configuration back showed exactly what had been asked for. The working value is the UTC equivalent: `16:00–23:59` yields 09:00–15:00 in Los Angeles.
- Also set **`round_to`** (60 for on-the-hour). Without it Nylas steps hourly from *now*, so slot times are whatever minute the page was loaded — 15:45, 16:45 — and differ on every visit.

**Resolved: working hours are ours to apply, not Nylas's.** They are declared per listing when a coach creates the session, stored on the listing as `publicData.nylasOpenHours` (`{days, start, end}` in the coach's own timezone), and applied by `filterSlotsByOpenHours` in the availability endpoint alongside the notice filter. **`default_open_hours` is deliberately never set on a configuration.**
  - This is what makes daylight saving a non-issue. Each slot is evaluated against the coach's own week, so `Intl` applies whatever offset was in force on that date — a slot in October and one in December each get the right answer, with nothing to re-sync. Writing a UTC window into Nylas instead would drift an hour at every transition. A test across the day London leaves BST covers this.
  - Verified against live data: clearing the stale window raised Nylas's raw slots from 70 to 168 (24/7), our filter cut those to 40, and the hours offered became 09:00–16:00 in the coach's zone. Note 16:00 — a session starting then ends exactly at the 17:00 close, and Nylas's UTC window had been silently dropping it, so our filter is not merely equivalent but more correct.
  - **To clear a configuration that already carries one, PUT `default_open_hours: []`.** A plain PUT merges rather than replaces, so simply omitting the field leaves the old window in place — which is how a stale UTC window survived several re-syncs and made an earlier test pass for the wrong reason.

**The Integration API is wired and verified.** Credentials live at `op://Revie Dev/sharetribe_dev_nylas/{client_id,client_secret}` and are referenced from `.env` as `SHARETRIBE_INTEGRATION_CLIENT_ID` / `_SECRET`. Verified against the live API: they authenticate as the `Revie Dev` marketplace and can read transactions. This is a **separate Console application** from the Marketplace API credentials, created under Build → Applications → Integration API, and it exists because `getTrustedSdk` exchanges the *logged-in user's* cookie token and so cannot act for a webhook, which has no user. It can act as operator on any transaction in the environment, so it is confined to `server/api/nylas/` and never reachable from the browser.

**The booking loop is complete in code**, though not yet exercised end to end because that needs the booking UI. `booking.created` records the mapping and calls `transition/operator-accept`, confirming the booking and capturing payment. `booking.cancelled` more than 48 hours out calls `transition/cancel` and refunds; inside 48 hours it deliberately calls nothing, letting the transaction complete by itself. `booking.rescheduled` is recorded only — Sharetribe booking times cannot be changed in place, so reschedules still need their own design. A 409 from Sharetribe is treated as success rather than failure, since it means a redelivered webhook is trying to repeat a transition already made.

**Nylas credentials are wired.** The API key and client ID live in the `Revie Dev` 1Password vault and are referenced from `.env` as `NYLAS_API_KEY` and `NYLAS_CLIENT_ID`, alongside `NYLAS_API_BASE_URL=https://api.us.nylas.com`. Note these deliberately carry **no `REACT_APP_` prefix**: that prefix is what copies a variable into the public browser bundle, so applying it to the API key would publish the key on the next deploy. The key is verified working against the US region.
